# Use heuristic text-pattern matching, not fail-closed flagging or a bashlex AST parser, for non-Python bundled script detection in find_network_drift

## Status

Proposed

## Context and Problem Statement

Retrofit record: this decision is already implemented (issue [#1079](https://github.com/tvna/gitapex/issues/1079), closed via PR [#1080](https://github.com/tvna/gitapex/pull/1080), merged). This ADR documents rationale that currently lives as prose inside `skills/evaluating-skill-quality/scripts/gitapex_scan_execution_requirements_drift.py`'s own module docstring and inline comments, written after the fact rather than before the decision was made.

`find_network_drift`'s AST-based lane (see [ADR 0003](0003-use-static-ast-not-dynamic-detection-for-network-drift.md)) only reads `skill_dir/scripts/*.py` -- a bundled non-Python script (a `.sh` file, for instance; this repository's own `skills/executing-a-branch-plan/scripts/check_task_bash_safety.sh` is one real example) cannot be AST-parsed at all, and was silently scored clean. This was inconsistent with this same module's own stated and tested principle for Python scripts: an unparseable/unreadable `.py` file is surfaced as an `error`-severity "undetermined, not clean" finding, never silently assumed safe. A live, primary-source-grounded trade-off investigation (conducted in the session that opened issue #1079) considered how to close this gap without violating the scanner's existing constraints: it must never execute a skill's bundled scripts (the same read-only, pre-execution invariant ADR 0003 documents), and this MIT-licensed repository has zero GPL dependencies today, with one open, unrelated bug (issue #1076) about an already-undeclared runtime dependency (PyYAML) that a second poorly-declared dependency would compound.

## Considered Options

- Fail-closed "undetermined" flagging with zero content analysis -- extend the existing unparseable-`.py` treatment to every non-Python file under `scripts/`
- `bashlex`-based AST parsing of shell scripts, for parity with the Python AST lane's own deterministic precision
- Heuristic text-pattern matching for network-capable command names, analogous to `find_tools_drift`'s own existing SKILL.md prose lane (already an accepted `kind: "heuristic"` precedent in this codebase)

## Decision Outcome

We will detect network-capable command usage in non-Python bundled scripts via a heuristic text-pattern lane (`_NETWORK_COMMAND_PATTERN`, matching `curl`/`wget`/`nc`/`ncat`/`netcat`/`ssh`/`scp`/`sftp`/`ftp`/`telnet`), checked against all three `network.mode` values and tagged `kind="heuristic"`, because:

- Fail-closed flagging was rejected: it would produce an `error`-severity finding for every skill with any benign non-Python script (one with zero network/write/shell capability), a false-positive cost judged too high to adopt as the fix itself.
- `bashlex` was rejected: it would be this repository's first GPLv3 dependency, with no license-compatibility sign-off given, and it would compound this scanner's own already-open, unrelated undeclared-runtime-dependency bug (issue #1076) with a second such dependency.
- The heuristic lane adds zero new dependencies (Python stdlib `re`/`pathlib`/`urllib.parse` only, already imported) and reuses this module's own already-accepted `kind: "heuristic"` tier rather than inventing a new evidence class.

This was not adopted on a first pass and trusted blind: two independent adversarial `/code-review` rounds against the implementing diff found and fixed four real, live-reproduced bugs before merge -- (1) a comment-only mention of `curl`/`wget` in this repository's own `check_task_bash_safety.sh` (a script that documents the exact fetch-and-execute pattern it exists to block) was originally misread as real usage; (2) a non-script binary asset under `scripts/` (e.g. a bundled image) was misread as an unreadable "script" and flagged; (3) an unreadable script under `network.mode: unrestricted` produced a self-contradicting error-plus-warning pair; (4) `allowlist` mode had zero coverage for non-Python scripts at all, the safety-relevant under-declaration direction left entirely unenforced. All four are fixed and each carries its own dedicated regression test.

The lane also mirrors several of the AST lane's own already-fixed correctness properties: a bundled non-Python file named `test_*` is excluded (mirroring the Python test-file exclusion); only a file that looks like a real bundled script -- a known extension (`_SCRIPT_EXTENSIONS`) or a leading shebang -- is read at all, so a non-script asset is never misclassified; an unreadable recognized script is surfaced as its own `non-python-script-unreadable` finding rather than scored clean; and whole-line comments are stripped before matching, using per-language comment syntax (`#` for shell/Ruby/Perl/PowerShell, `//` additionally for JavaScript/TypeScript/PHP, `REM`/`::` for Windows batch) rather than one pattern applied unconditionally.

## Consequences

Good, because it closes the fail-open gap for non-Python bundled scripts with zero new dependencies, reusing this module's own already-accepted `kind: "heuristic"` evidence tier rather than inventing a new one.
Good, because the decision was adversarially hardened, not merely assumed correct: nine dedicated tests (`test_non_python_bundled_scripts_get_heuristic_network_scan`, `test_benign_non_python_bundled_script_produces_no_finding`, `test_non_python_test_file_is_excluded_from_network_scan`, `test_non_script_asset_under_scripts_dir_produces_no_finding`, `test_non_python_comment_only_network_mention_produces_no_finding`, `test_non_python_slash_comment_only_network_mention_produces_no_finding`, `test_unreadable_non_python_script_is_undetermined_not_clean`, `test_unreadable_script_suppresses_unrestricted_over_declared_warning`, `test_non_python_allowlist_mode_flags_out_of_list_host`) each pin one of the four adversarially-found bugs fixed, or one of the lane's own positive/negative-case guarantees, concretely rather than only in prose.
Good, because it is symmetric with the AST lane's own undetermined-on-unparseable treatment: an unreadable recognized script produces its own `non-python-script-unreadable` finding and suppresses the `unrestricted`-mode over-declaration warning, the same way `network-script-unparseable` already does for an unparseable `.py` file -- no contradictory error-plus-warning pair.
Bad, because this is still a text heuristic, not a parser: a network-capable command invoked indirectly (an alias, a variable, a wrapper function) evades `_NETWORK_COMMAND_PATTERN` entirely, the same evasion class already accepted for `find_tools_drift`'s own SKILL.md prose lane and for the AST lane's own runtime-constructed-host gap (ADR 0003).
Bad, because the opposite-direction imprecision is real too: a command name or URL quoted as plain text inside an unrelated string/regex literal on a real code line (not a comment) still matches and produces a finding -- proven concretely by `test_non_python_quoted_network_command_text_still_produces_finding` (constructed directly against `check_task_bash_safety.sh`'s own `fetch_exec_re` variable, which legitimately quotes `"curl|wget"` as detection text, not as an invocation) rather than only asserted. Disclosed as an accepted residual limitation, not chased with a full shell/string-literal parser disproportionate to a best-effort tier.
Bad, because `_looks_like_bundled_script`'s extension-or-shebang gate is not exhaustive: a real script in an unlisted language with no shebang line is still invisible to this lane entirely, the same disclosed language-scope gap the rest of this module already carries.
Bad, because `find_tools_drift`'s own analogous non-Python blind spot (write/shell capability detection for non-Python scripts) remains unaddressed -- explicitly out of scope per issue #1079's own Non-goals, tracked as a separate, not-yet-filed follow-up.

## Confirmation

The nine tests named above in the first Good consequence are real, existing tests in `skills/evaluating-skill-quality/scripts/test_gitapex_scan_execution_requirements_drift.py` that pin both this decision's positive capability (real network-capable non-Python content is caught under `disabled` and `allowlist` modes) and its known, disclosed limits (the Bad consequences above) -- a future change to this lane that silently narrows or widens those limits would need to update these tests deliberately rather than by accident. No mechanism currently confirms this lane's own scope boundary (that it never attempts to execute or fully parse a non-Python script) beyond code review and the two adversarial `/code-review` rounds already run against the implementing diff -- relies on review for that specific property, the same reliance ADR 0003 already discloses for the AST lane's own never-execute invariant.
