# Use static analysis, not dynamic execution or fail-closed flagging, for find_network_drift's detection mechanism

## Status

Proposed

## Context and Problem Statement

Retrofit record: both decisions this ADR documents are already implemented -- the Python-script lane (issue [#1022](https://github.com/tvna/gitapex/issues/1022), closed via PR [#1027](https://github.com/tvna/gitapex/pull/1027), merged) and the non-Python bundled-script lane (issue [#1079](https://github.com/tvna/gitapex/issues/1079), closed via PR [#1080](https://github.com/tvna/gitapex/pull/1080), merged). This ADR documents rationale that currently lives as prose inside `skills/evaluating-skill-quality/scripts/gitapex_scan_execution_requirements_drift.py`'s own module docstring, written after the fact rather than before either decision was made. Originally drafted as two separate ADRs (0003 for the Python lane, 0004 for the non-Python lane); consolidated into one record at the requester's own direction, since both are the same scanner function's detection-method decision, split only by which script language it is detecting against, not by a different underlying constraint.

Issue #1022 requested a companion scanner cross-checking a skill's declared `spec.executionRequirements.network` (mode/domains) against what its bundled `scripts/*` actually do, catching the case where a skill declares `network.mode: disabled` while a bundled script performs real network I/O. The scanner (`find_network_drift`) must operate as a read-only, pre-execution check: per its own module docstring, it "must never itself run a skill's bundled scripts" -- the skill directories it scans are untrusted content from the reviewer's own threat model (a skill's bundled script could itself be adversarial or simply buggy), so executing them to observe behavior is not an option for either script language.

Python scripts (`scripts/*.py`) can be parsed by Python's own `ast` module, giving a real, native parse tree. Non-Python scripts (`scripts/*.sh` and other shell/scripting-language files -- this repository's own `skills/executing-a-branch-plan/scripts/check_task_bash_safety.sh` is one real example) cannot be AST-parsed by Python's own stdlib at all, and were originally invisible to this scanner entirely -- silently scored clean, inconsistent with this same module's own stated and tested principle for Python scripts (an unparseable/unreadable `.py` file is surfaced as an `error`-severity "undetermined, not clean" finding, never silently assumed safe). Closing that gap (issue #1079) required a second, independent detection decision, since the tooling and constraints differ by language: it needed to avoid a new third-party dependency (this MIT-licensed repository has zero GPL dependencies today, and this scanner already has one open, unrelated bug -- issue #1076 -- about an already-undeclared runtime dependency, PyYAML, that a second poorly-declared dependency would compound), and needed to avoid the high false-positive cost of a purely fail-closed treatment.

A live design discussion on issue #1022 researched whether a dynamic/DAST-style approach -- including running a bundled script inside an isolated sandbox to observe its real behavior while containing the blast radius of that execution -- could replace or improve on static analysis for the Python lane specifically.

## Considered Options

**For Python bundled scripts (`scripts/*.py`):**
- Python's own `sys.addaudithook` (PEP 578) to observe network-related events at runtime
- Established DAST (Dynamic Application Security Testing) tooling
- Sandboxed/isolated execution (a container, OS-level namespace, or a similarly restricted subprocess) to observe a bundled script's real behavior while containing its blast radius
- Static analysis via Python's own `ast` module (stdlib)

**For non-Python bundled scripts (`.sh` and other shell/scripting-language files):**
- Fail-closed "undetermined" flagging with zero content analysis -- extend the existing unparseable-`.py` treatment to every non-Python file under `scripts/`
- `bashlex`-based AST parsing of shell scripts, for parity with the Python lane's own deterministic precision
- Heuristic text-pattern matching for network-capable command names, analogous to `find_tools_drift`'s own existing SKILL.md prose lane (already an accepted `kind: "heuristic"` precedent in this codebase)

## Decision Outcome

**Python lane:** We detect network-capable imports and literal `https?://` hosts via static AST parsing (Python's own `ast` module, stdlib), because all three alternatives require the target code to actually execute -- in full or inside an isolated copy -- to produce a signal, which is fundamentally incompatible with this scanner's own read-only, pre-execution safety constraint:

- `sys.addaudithook`'s own [PEP 578](https://peps.python.org/pep-0578/) documentation states plainly it is "not suitable for implementing a 'sandbox'" and only fires when the audited code path actually runs.
- Established DAST tooling targets a *running* application's own HTTP/UI surface -- there is no running application here, only a skill directory's static file content.
- A sandbox narrows the blast radius of running untrusted code; it does not eliminate the act of running it, which is exactly what this scanner's own stated invariant -- "must never itself run a skill's bundled scripts" (Context, above) -- exists to prevent. General-purpose isolation technology (containers, seccomp-bpf, gVisor-style user-space kernels) has a documented history of escape vulnerabilities, so "sandboxed" reduces the risk of executing adversarial code, it does not remove it. A sandbox harness is also itself a nontrivial, environment-dependent piece of infrastructure -- namespace/container-runtime availability, privilege level, and syscall-filtering support all vary by host -- working against this scanner's own portability requirement to run the same way across arbitrary CI runners, contributor machines, and restricted execution surfaces (`evaluating-skill-quality`'s own `spec.portability`), unlike `ast`, which is stdlib and runs identically in any Python 3 interpreter with no elevated privileges.

A real AST parse tree also has no comment nodes at all, so a commented-out reference can never register as usage without a filter having to say so, and the parser correctly distinguishes each real import syntax shape (`import X`, `import X.Y`, and `from X import Y` are each walked as their own distinct `ast.Import`/`ast.ImportFrom` node, not approximated by one regex trying to cover all three) before checking the parsed dotted module name against a fixed allowlist (`NETWORK_CAPABLE_MODULES`) -- string-membership matching, not Python's own runtime import resolution (which additionally handles `sys.path`, relative imports, and re-exports this scanner has no need to reproduce).

**Non-Python lane:** We detect network-capable command usage via a heuristic text-pattern lane (`_NETWORK_COMMAND_PATTERN`, matching `curl`/`wget`/`nc`/`ncat`/`netcat`/`ssh`/`scp`/`sftp`/`ftp`/`telnet`), checked against all three `network.mode` values and tagged `kind="heuristic"`, because:

- Fail-closed flagging was rejected: it would produce an `error`-severity finding for every skill with any benign non-Python script (one with zero network/write/shell capability), a false-positive cost judged too high to adopt as the fix itself.
- `bashlex` was rejected: as of this evaluation (2026-08-13), `bashlex` 0.18 is licensed GPLv3+ per its own [`setup.py`](https://github.com/idank/bashlex/blob/master/setup.py) and [`LICENSE`](https://github.com/idank/bashlex/blob/master/LICENSE) file. This repository's `pyproject.toml` declares zero root `dependencies` and a `dependency-groups.dev` list of fifteen packages (pytest, pytest-cov, pytest-xdist, pytest-split, hypothesis, pyyaml, prek, jsonschema, pydantic, mypy, types-PyYAML, types-jsonschema, ruff, radon, xenon), none GPL-licensed -- so "zero GPL dependencies" covers both the empty runtime set and the declared dev group; `bashlex` was not checked against `uv.lock`'s full transitive closure, since it was never added. Adding it would be this repository's first GPLv3 dependency at any tier, with no license-compatibility sign-off given, and it would compound this scanner's own already-open, unrelated undeclared-runtime-dependency bug (issue #1076) with a second such dependency.
- The heuristic lane adds zero new dependencies (Python stdlib `re`/`pathlib`/`urllib.parse` only, already imported) and reuses this module's own already-accepted `kind: "heuristic"` tier rather than inventing a new evidence class.

This was not adopted on a first pass and trusted blind: two independent adversarial `/code-review` rounds against the implementing diff found and fixed four real, live-reproduced bugs before merge -- (1) a comment-only mention of `curl`/`wget` in this repository's own `check_task_bash_safety.sh` (a script that documents the exact fetch-and-execute pattern it exists to block) was originally misread as real usage; (2) a non-script binary asset under `scripts/` (e.g. a bundled image) was misread as an unreadable "script" and flagged; (3) an unreadable script under `network.mode: unrestricted` produced a self-contradicting error-plus-warning pair; (4) `allowlist` mode had zero coverage for non-Python scripts at all, the safety-relevant under-declaration direction left entirely unenforced. All four are fixed and each carries its own dedicated regression test.

The non-Python lane also mirrors several of the Python lane's own already-fixed correctness properties: a bundled non-Python file named `test_*` is excluded (mirroring the Python test-file exclusion); only a file that looks like a real bundled script -- a known extension (`_SCRIPT_EXTENSIONS`) or a leading shebang, checked by `_looks_like_bundled_script` -- is read at all, so an asset with neither a known script extension nor a leading shebang is skipped entirely (a recognized-extension file that turns out not to be readable UTF-8 text still surfaces as its own `non-python-script-unreadable` finding, the same "undetermined, not clean" treatment the Python lane gives an unparseable `.py` file -- not a silent skip); whole-line comments are stripped before matching, using per-language comment syntax (`#` for shell/Ruby/Perl/PowerShell, `//` additionally for JavaScript/TypeScript/PHP, `REM`/`::` for Windows batch) rather than one pattern applied unconditionally.

## Consequences

Good, because neither lane ever needs to execute a skill's bundled scripts to produce a finding, holding the read-only safety constraint exactly across both languages.
Good, because the Python lane's real parse tree gives exact, deterministic results for the shapes it does cover (same input always parses to the same finding) -- no reliance on brittle text-regex approximations of import syntax; unlike a text-regex scan, `ast.walk` also sees every import/call regardless of surrounding control flow (an `if False:`-guarded import is still a real `ast.Import` node in the tree), so conditional gating does not, by itself, evade this lane -- verified directly: `ast.walk(ast.parse("if False:\n    import requests"))` still yields the `Import` node.
Good, because the non-Python lane was adversarially hardened, not merely assumed correct: ten dedicated tests (`test_non_python_bundled_scripts_get_heuristic_network_scan`, `test_benign_non_python_bundled_script_produces_no_finding`, `test_non_python_test_file_is_excluded_from_network_scan`, `test_non_script_asset_under_scripts_dir_produces_no_finding`, `test_non_python_comment_only_network_mention_produces_no_finding`, `test_non_python_slash_comment_only_network_mention_produces_no_finding`, `test_unreadable_non_python_script_is_undetermined_not_clean`, `test_unreadable_script_suppresses_unrestricted_over_declared_warning`, `test_non_python_allowlist_mode_flags_out_of_list_host`, `test_non_python_quoted_network_command_text_still_produces_finding`) each pin one of the four adversarially-found bugs fixed, one of the lane's own positive/negative-case guarantees, or the disclosed residual limitation two entries below -- concretely rather than only in prose.
Good, because the non-Python lane is symmetric with the Python lane's own undetermined-on-unparseable treatment: an unreadable recognized script produces its own `non-python-script-unreadable` finding and suppresses the `unrestricted`-mode over-declaration warning, the same way `network-script-unparseable` already does for an unparseable `.py` file -- no contradictory error-plus-warning pair.
Bad, because Python-lane static analysis cannot see every real network-capable call shape: a call routed through an unlisted helper function, or a host built at runtime (string concatenation, an f-string with a non-literal segment) can still slip past AST analysis exactly as it would past a human reading the same source. This is disclosed in the scanner's own docstring and demonstrated by a deliberately-constructed test (`test_dynamically_constructed_host_evades_allowlist_check`).
Bad, because the non-Python lane is still a text heuristic, not a parser: a network-capable command invoked indirectly (an alias, a variable, a wrapper function) evades `_NETWORK_COMMAND_PATTERN` entirely, the same evasion class already accepted for `find_tools_drift`'s own SKILL.md prose lane and for the Python lane's own runtime-constructed-host gap above.
Bad, because the non-Python lane's opposite-direction imprecision is real too: a command name or URL quoted as plain text inside an unrelated string/regex literal on a real code line (not a comment) still matches and produces a finding -- proven concretely by `test_non_python_quoted_network_command_text_still_produces_finding` (constructed directly against `check_task_bash_safety.sh`'s own `fetch_exec_re` variable, which legitimately quotes `"curl|wget"` as detection text, not as an invocation) rather than only asserted. Disclosed as an accepted residual limitation, not chased with a full shell/string-literal parser disproportionate to a best-effort tier.
Bad, because `_looks_like_bundled_script`'s extension-or-shebang gate is not exhaustive: a real script in an unlisted language with no shebang line is still invisible to the non-Python lane entirely, the same disclosed language-scope gap the rest of this module already carries.
Bad, because `find_tools_drift`'s own analogous non-Python blind spot (write/shell capability detection for non-Python scripts) remains unaddressed -- explicitly out of scope per issue #1079's own Non-goals, tracked as a separate, not-yet-filed follow-up.

## Confirmation

`test_dynamically_constructed_host_evades_allowlist_check` pins the Python lane's own known limit (Bad consequence above); the ten tests named in the second Good consequence above pin both the non-Python lane's positive capability (real network-capable non-Python content is caught under `disabled` and `allowlist` modes) and its own known, disclosed limits -- a future change to either lane that silently narrows or widens these limits would need to update these tests deliberately rather than by accident. No mechanism currently confirms either lane's own scope boundary (that the scanner never attempts to execute or fully parse a bundled script) beyond code review and, for the non-Python lane specifically, the two adversarial `/code-review` rounds already run against its implementing diff -- both lanes rely on review for that specific property.
