# scanning-ci-workflows: Implementation Plan

**Goal:** Ship `skills/scanning-ci-workflows/`, the first skill in the
`scanning-*` family to actually delegate judgment to an external pinned
CLI, orchestrating zizmor and actionlint over a target repository's
GitHub Actions workflow files -- and land zizmor in the toolchain in the
same change, so it is never "pinned but unwired" the way `betterleaks`
is today. Source: https://github.com/tvna/gitapex/issues/847.

**Architecture:** One new skill directory (`SKILL.md`,
`metadata/gitapex.yaml`, `references/worked-examples.md`), one new eval
corpus (`evals/scanning-ci-workflows/`), one toolchain change
(`flake.nix` + its smoke test), and three documentation updates whose
existing text explicitly anticipates this skill shipping. No new
`scripts/` -- this skill runs two external binaries; it ships no checker
of its own.

**Tech Stack:** Plain Markdown + YAML + one Nix package attribute. No new
Python dependency.

## Global constraints (from the issue)

- `write: []` always. This is a real boundary, not a formality: zizmor
  ships `--fix` (safe/unsafe/all), so "report-only" has to be enforced by
  the skill's own Stop boundaries, not assumed from the tool's nature.
- Cite the capability-selection policy document rather than re-deriving
  the libre-CLI-first rule or the platform-detection mechanism inline.
- Knowledge of what makes a workflow unsafe stays in zizmor/actionlint.
  This skill's own `references/` records *invocation and reporting*
  evidence, never a catalogue of unsafe workflow patterns.
- No absorption of `auditing-git-hosting-surface`; no `shell: [zizmor]`
  added to `scanning-attack-surfaces`; no auto-remediation; no third
  tool; no platform-native-capability detection.
- Keep every GitHub-facing artifact ASCII.

## Deviation from the issue's Acceptance Criteria Map, disclosed

The ACM's last row reads "`write: []` always; no `network` declared", with
the interpretation "needs no live network access (both tools are local
static analyzers)". The second half of that interpretation is factually
wrong (see the Facts table above). The *intent* -- this skill must not
reach the network -- is honored exactly; the mechanism changes:

- `metadata/gitapex.yaml` declares `executionRequirements.network.mode:
  disabled` rather than omitting the block. Per the metadata schema's own
  wording, an absent `network` block means "not yet declared", while
  `disabled` means "declared, network prohibited". For a skill wrapping a
  network-capable tool, only the latter states the real contract.
- `SKILL.md`'s Procedure passes `--offline` to zizmor unconditionally,
  and its Stop boundaries forbid supplying a GitHub token, so the
  declaration is enforced rather than aspirational.
- The five offline-unavailable audits are reported as a named coverage
  Gap in every run, never silently dropped.

## Irreversibility classification

Every task writes only tracked files inside this repository's working
tree on a feature branch. No task deletes data, rotates a credential,
publishes a release, or touches anything outside the repository. No task
is classified irreversible, so no task needs a fresh per-task
confirmation.
