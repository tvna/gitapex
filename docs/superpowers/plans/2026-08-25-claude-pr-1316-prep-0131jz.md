## Task 2 -- Differential-parsing oracle (`unidiff`, dev-only)

**Cites ACM row:** "The Hypothesis property suites covering every
`parse_added_lines`-family parser must gain an independent oracle capable
of catching a misattribution-class defect..." (Row 2).

**Quoted Planned ops (verbatim from the issue body):** "`uv add --dev
unidiff` ...; a new differential property-test function per diff-parsing
test file today ...".

**Files:** `pyproject.toml`,
`tests/test_gitapex_gate_detection_logic_property_coverage_properties.py`,
`tests/test_gitapex_gate_exception_handler_gaps_properties.py`,
`tests/test_gitapex_gate_stdlib_only_claim_drift_properties.py` (new).

**Design, fixed at decomposition time:**
- Add `"unidiff>=0.7"` to `[dependency-groups].dev` in `pyproject.toml`
  (dev-only, matching the issue's own explicit constraint -- never a
  production dependency), with a short comment citing issue #1316 and the
  PyPI verification (MIT, zero runtime deps).
- For each of the three diff-parsing functions
  (`gitapex_gate_detection_logic_property_coverage.parse_added_lines`,
  `gitapex_gate_exception_handler_gaps.parse_added_lines`,
  `gitapex_gate_stdlib_only_claim_drift.parse_diff_added_third_party_imports`),
  add one Hypothesis property comparing the in-house parser's own
  per-file added-line output against `unidiff.PatchSet`'s own independent
  parse of the identical generated diff text, reusing each file's own
  existing diff-generation strategy (`_MULTI_FILE_DIFFS`/`_file_diff_text`
  for the two existing property files; a new, analogous strategy for the
  third, new property file, matching `_diff`'s own header/hunk shape from
  `tests/test_gitapex_gate_stdlib_only_claim_drift.py`).
- True-positive proof: run the new property (or a fixed, non-Hypothesis
  regression case using the exact same fixture) against
  `gitapex_gate_stdlib_only_claim_drift`'s pre-task-1-fix behavior --
  confirmed by temporarily reverting task-1's one-line fix in a scratch
  copy or by asserting directly against the pre-fix diff shape from the
  issue's own reproduction steps -- and confirm the oracle reports a real
  mismatch (unidiff finds the added import; the in-house parser does not).
  Record this proof in the task's own commit message, not as a permanent
  test parametrized on "pre-fix code" (task-1 has already landed the fix
  in the tree by the time task-2 runs).
- True-negative proof: the new property must also pass (no mismatch)
  against ordinary, well-formed generated diffs across many Hypothesis
  examples -- covered by the property itself running at
  `settings(derandomize=True, max_examples=200, deadline=None)`, matching
  each file's own existing `_PROPERTIES` convention.

**Proof method:** `uv run --frozen pytest tests/ -k "properties" -v` --
all three property files' full suites green, including the three new
differential properties; a documented true-positive check (per bullet
above) recorded in the task's own commit message.

## Task 3 -- Scheduled deep-scan workflow (higher exploration, non-blocking)

**Cites ACM row:** "A scheduled, non-PR-blocking CI job should re-run the
same property suites with substantially higher exploration..." (Row 3).

**Quoted Planned ops (verbatim from the issue body):** "A new
`.github/workflows/*.yml` scheduled (e.g. nightly or weekly) trigger;
reuses the existing ... property test files as-is, invoked with different
Hypothesis settings via an environment variable or a separate settings
profile, rather than duplicating the test bodies."

**Files:** `.github/workflows/diff-parsing-property-deep-scan.yml` (new).

**Design, fixed at decomposition time:** follow
`.github/workflows/retrospective-gate-drift.yml`'s own shape (harden-checkout
action pinned to `main`, `astral-sh/setup-uv`, `schedule:` cron +
`workflow_dispatch: {}`, `concurrency` group, minimal `permissions:
contents: read`). Re-run the three property test files from task-2 (plus
their two pre-existing hosts) via an environment variable
(`GITAPEX_HYPOTHESIS_DEEP_SCAN=1`) read by each property file's own
`_PROPERTIES` settings object -- `derandomize` flips to `False` and
`max_examples` rises substantially (e.g. 5000) only when that variable is
set, leaving the PR-blocking gate's own pinned
`derandomize=True, max_examples=200` completely unchanged for ordinary
CI. This requires a small, shared, additive edit to each of the three
property files' own `_PROPERTIES` line (not a task-2 regression -- task-2
already added the new differential property to each file; task-3 only
makes the *existing* `_PROPERTIES` settings object env-var-aware).
Informational only for its first landing (mirrors
`retrospective-gate-drift.yml`'s own citation-drift step, which does fail
the run on threshold -- but issue #1316's own ACM Row 3 proof method is
only "confirmed to run to completion," not auto-filing on failure; auto-
filing is named in the issue's own residual-risk column as a future
gap, not required by this task's own proof method) -- the job still fails
on a genuine new counterexample (an uncaught exception/assertion failure
surfaces as a normal pytest failure, same as any other scheduled test
job), it simply is not additionally wired to auto-file an issue on that
failure in this pass.

**Proof method:** a manual `workflow_dispatch` trigger of the new
workflow (via the GitHub connector's actions-run-trigger call), confirmed
to run to completion and report cleanly against current `main` post-merge
-- deferred to `drafting-a-pr-to-merge`'s own CI-driving loop, since the
workflow cannot be manually dispatched against a ref that does not yet
exist on the remote until this branch is pushed; local proof for this
task is `uv run --frozen env GITAPEX_HYPOTHESIS_DEEP_SCAN=1 pytest tests/ -k "properties" -v`
completing (not necessarily fast) with the higher example count actually
in effect (confirmed via a print/log line or by temporarily lowering the
deep-scan `max_examples` for the local proof run only, reverted before
commit).
