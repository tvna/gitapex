## 2. Waza standalone-run check (Step 1)

**Host note:** this spike ran on macOS/arm64 (`uname -m` → `arm64`), not
Linux as the brief's literal commands assume. A Linux binary will not execute
on macOS, so the darwin-matching asset was downloaded instead for the
standalone-run proof. The Linux asset was still inspected for its archive
*layout* in Step 2 below (layout is OS-arch-independent for this tool's
packaging).

**Surprise:** the darwin waza assets are `.zip`, not `.tar.gz`. The full
asset list for tag `azd-ext-microsoft-azd-waza_0.38.0`:

```
microsoft-azd-waza-darwin-amd64.zip
microsoft-azd-waza-darwin-arm64.zip
microsoft-azd-waza-linux-amd64.tar.gz
microsoft-azd-waza-linux-arm64.tar.gz
microsoft-azd-waza-windows-amd64.zip
microsoft-azd-waza-windows-arm64.zip
```

Commands run:
```bash
curl -fsSL -o waza.zip "https://github.com/microsoft/waza/releases/download/azd-ext-microsoft-azd-waza_0.38.0/microsoft-azd-waza-darwin-arm64.zip"
unzip -o waza.zip -d extracted
chmod +x extracted/microsoft-azd-waza-darwin-arm64
./extracted/microsoft-azd-waza-darwin-arm64 --version
./extracted/microsoft-azd-waza-darwin-arm64 check --help
```

Result:
- `--version` → `waza version 0.38.0` (exit 0) — matches the release tag.
- `check --help` → prints full usage text (flags `--format`, `--debug`,
  `--no-update-check`, examples like `waza check code-explainer`), **exit 0,
  no azd runtime present**. This confirms `waza check` runs standalone.
- The archive also contains an `extension.yaml` (azd extension manifest,
  irrelevant to the standalone Nix package — not the binary).

**Executable-bit surprise:** inside the zip, `zipinfo -l` shows the entry as
filesystem type `fat` with unix perm bits not preserved
(`-rw----` on the stored central-directory record). `unzip` alone does not
mark the extracted file executable — an explicit `chmod +x` (or
`install -Dm755`) is required in the darwin `installPhase`. This is unlike
the Linux `tar.gz` below, whose entries carry the executable bit natively.

## 3. Class B archive layouts (Step 2)

All Linux archives were listed with `tar tzvf` (verbose, to see perm bits)
rather than the brief's plain `tar tz`, to also confirm the executable bit
survives inside each `tar.gz` (relevant for whether `installPhase` needs an
explicit `chmod`).

| tool | archive | layout | binary path | executable bit in archive | special dirs |
|---|---|---|---|---|---|
| waza (linux-amd64) | `microsoft-azd-waza-linux-amd64.tar.gz` | **bare / root** — needs `sourceRoot = "."` | `microsoft-azd-waza-linux-amd64` | yes (`-rwxr-xr-x`) | `extension.yaml` also at root (unused by standalone package) |
| waza (darwin-arm64) | `microsoft-azd-waza-darwin-arm64.zip` | **bare / root** — needs `sourceRoot = "."` | `microsoft-azd-waza-darwin-arm64` | **no** — zip does not preserve unix perms; `chmod +x` required in installPhase | `extension.yaml` also at root |
| apm | `apm-linux-x86_64.tar.gz` | **subdirectory** `apm-linux-x86_64/` (NOT bare — do not set `sourceRoot = "."`; the default single top-level dir works) | `apm-linux-x86_64/apm` | yes (`-rwxr-xr-x`) | **`apm-linux-x86_64/_internal/`** — large PyInstaller "onedir" frozen-bundle support tree (157 entries total in the archive: compiled `.so` extensions, `.dist-info` metadata, bundled `scripts/runtime/*.sh`/`.ps1` setup scripts, etc.). The `apm` executable is a **thin loader that requires `_internal/` to sit alongside it at runtime** — the installPhase must copy the whole subdirectory tree (both `apm` and `_internal/`), not just the binary, then symlink/wrap only `apm` onto `$out/bin`. |
| rtk | `rtk-x86_64-unknown-linux-musl.tar.gz` | **bare / root** — needs `sourceRoot = "."` | `rtk` | yes (`-rwxr-xr-x`) | none — single static binary |
| betterleaks | `betterleaks_1.6.1_linux_x64.tar.gz` | **bare / root** — needs `sourceRoot = "."` | `betterleaks` | yes (`-rwxr-xr-x`) | `LICENSE`, `README.md` alongside the binary at root (unused by installPhase, but present — do not assume the root contains only the binary) |

Commands run (per tool, `tar tzvf` piped from `curl`):
```bash
curl -fsSL "$base_waza/microsoft-azd-waza-linux-amd64.tar.gz" | tar tzvf -
curl -fsSL "$base_apm/apm-linux-x86_64.tar.gz" | tar tzvf - | grep -v '_internal/'
curl -fsSL "$base_rtk/rtk-x86_64-unknown-linux-musl.tar.gz" | tar tzvf -
curl -fsSL "$base_bl/betterleaks_1.6.1_linux_x64.tar.gz" | tar tzvf -
```
where:
```bash
base_waza="https://github.com/microsoft/waza/releases/download/azd-ext-microsoft-azd-waza_0.38.0"
base_apm="https://github.com/microsoft/apm/releases/download/v0.25.0"
base_rtk="https://github.com/rtk-ai/rtk/releases/download/v0.43.0"
base_bl="https://github.com/betterleaks/betterleaks/releases/download/v1.6.1"
```

Full `apm-linux-x86_64.tar.gz` entry count: 157 (verified with
`tar tzf ... | wc -l`); only the top-level dir and the `apm` executable are
outside `_internal/`.

## 4. Summary for downstream tasks

- **Task 2** (flake scaffolding, Class A + channel pin): use
  `nixos-26.05` as the nixpkgs input ref. Verify Class A tool availability
  via `nix flake check` in CI, not locally (no local Nix on this host).
- **Task 3** (Class B `installPhase`s):
  - waza, rtk, betterleaks: all bare-root archives → `sourceRoot = "."` (or
    equivalent unpack override), then `install -Dm755 <binary-name> $out/bin/<name>`.
  - waza's darwin `.zip` build additionally needs an explicit `chmod +x`
    (or the `-Dm755` install mode, which sets the bit itself) since the
    executable bit is not preserved in the zip's central directory.
  - apm: do NOT flatten with `sourceRoot = "."` — the tarball's single
    top-level directory should be preserved so `_internal/` and `apm` land
    together in `$out/libexec/apm-linux-x86_64/` (or similar), with a
    thin `$out/bin/apm` wrapper/symlink pointing at the real executable in
    that directory. Copying only the `apm` binary out of context will break
    it at runtime (PyInstaller onedir bundles require `_internal/` as a
    sibling directory).
