# gitapex history

Maintainer-facing provenance for this repository's own history of
`battle-testing-a-skill`, moved out of `metadata/gitapex.yaml`'s
`spec.references` list because the full text of each entry below exceeds
that field's per-entry character budget. This is provenance for this
specific repository, not skill content the skill depends on to function.

## Clairvoyance corroboration and portability write-up

The clairvoyance project (public, MIT-licensed: https://github.com/tvna/clairvoyance) runs an adversarial "battle" harness over its own skills, described in `battle/README.md` as "a local, advisory harness that stress-tests the skills against hostile inputs -- separate from `waza`." Its five scenario categories (`scenarios/injection/`, `scenarios/guardrails/`, `scenarios/routing/`, `scenarios/depth-gate/`, `scenarios/encoding/`) recur across the extracted core here, which corroborates but does not originate this skill -- the mapping between the two category sets was previously carried as a table inside `adversarial-dimensions.md` and was removed from the distributed skill; this citation is its replacement, kept here as maintainer-facing corroboration rather than as skill content. The same project's portability write-up describes the exact failure this skill exists to fix: a foreign harness asked to evaluate a skill has no rubric injected and cannot say why a skill is weak.

## Held-out gate design lineage (issue 25, PR 29)

SKILL.md's "Connection to the held-out gate" section names `scorer-gated-skill-edits` as this repo's example of a skill consuming a battle-test verdict as a scorer, without an issue citation (kept portable). For readers working in this repository: that connection traces to https://github.com/tvna/gitapex/issues/25 (closed design issue, "design a held-out-gated skill-training loop, scoped to verifiable tasks"), whose component 2 this skill implements; `scorer-gated-skill-edits` itself is the component-1 implementation, landed via PR https://github.com/tvna/gitapex/pull/29.

## Self-audit tracking issue 261 deferred findings (issue 364)

https://github.com/tvna/gitapex/issues/261 deferred two findings from this file with a stated reason rather than resolving them there: dimension 14 (a dedicated regression corpus for this file's own guardrail prose, distinct from evals/battle-testing-a-skill/'s existing corpus that tests this skill's grading behavior against arbitrary fed-in targets) was handed to https://github.com/tvna/gitapex/issues/364; the CLAUDE.md-exclusion enforcement-hook question was decided, not deferred -- no hook was added, because a PreToolUse hook can inspect tool-call arguments but not the harness's auto-injected CLAUDE.md context, so it cannot verify the exclusion actually held from the tool-call surface alone. This boundary stays prose-only in gitapex today, backed by the observable check Procedure step 1 already requires, until a harness exposes a hookable signal for injected-context contents.

## CLAUDE.md-exclusion isolation drift fix (issue 475) and Codex review (PR 478)

https://github.com/tvna/gitapex/issues/475: Procedure step 1's own CLAUDE.md-exclusion paragraph pre-dated evaluating-skill-quality's references/adversarial-self-audit.md Isolation verification section (a live, per-platform registry plus a portable two-control verification procedure, added there in https://github.com/tvna/gitapex/issues/390) and had drifted from it -- step 1 still told the reader a filesystem-ancestry-only check on the scratch location was sufficient confirmation, which that registry's own Known entries section documents as insufficient (it missed a real leak on the one platform tested; only the dispatched agent's own self-report, via the two-control test, caught it). Fixed by having step 1 defer to that registry instead of re-deriving its own weaker check, reusing evaluating-skill-quality/SKILL.md's own already-shipped wording for the equivalent requirement rather than authoring new judgment content. skillDependencies.requires gained evaluating-skill-quality to reflect this functional dependency, matching evaluating-deterministic-gate-quality's and vetting-attack-surface's identical existing declaration for the same reason. A live reconfirmation trial ran this same session against the current platform (CLAUDE_CODE_REMOTE=true, CLAUDE_CODE_REMOTE_ENVIRONMENT_TYPE=cloud_default, claude 2.1.220 -- identical to the registry's existing dated entry): `claude -p` from this repository's own root quoted real CLAUDE.md text, and the identical prompt from a directly-confirmed CLAUDE.md/AGENTS.md-free working directory reported none loaded, reconfirming the registry's verified alternative still holds at this version (recorded in adversarial-self-audit.md itself, not duplicated here). evaluating-deterministic-gate-quality and vetting-attack-surface were also checked (grep across skills/ for the Subagent-dispatch/CLAUDE.md/AGENTS.md pattern) and already correctly defer to the same registry with no independent inline claim -- no change made to either. battle-testing-a-skill's own audit round was WAIVED for this fix (frontmatter description unchanged, so permitted per gate_skill_audit_disclosure.py's rule): the new step 1 text reuses already-audited wording lifted from evaluating-skill-quality/SKILL.md's own shipped Subagent dispatch section rather than introducing novel judgment-bearing content, the same class of waiver evaluating-deterministic-gate-quality's own https://github.com/tvna/gitapex/issues/455 entry above precedents for a structural, non-behavioral change. A same-PR external Codex review (PR https://github.com/tvna/gitapex/pull/478) correctly flagged that the first version of this fix named a specific sibling file and heading (evaluating-skill-quality's references/adversarial-self-audit.md Isolation verification section) in bare backtick prose -- more specific, and more fragile, than evaluating-deterministic-gate-quality's and vetting-attack-surface's own established phrasing, since no deterministic check (skill-dependencies-resolve checks only sibling-directory existence; links-inside-skill/anchor-targets-resolve only cover real Markdown links, which a cross-skill target cannot legally be under this repository's own Portable-link rule) would catch that file or heading later drifting. Fixed by backing off to the same lower-specificity, already-accepted phrasing the two sibling skills already use ("evaluating-skill-quality's own Subagent dispatch section"), matching this repository's existing accepted risk level rather than exceeding it, without inventing a new citation convention or checker feature in this PR. Whether a general deterministic drift-gate for this whole class of cross-skill prose citation (affecting three skills already, not only this one) should be built now or as its own follow-up issue was left to the operator's own call rather than decided unilaterally.
