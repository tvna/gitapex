Without the blank-line rule, two substrings sitting in adjacent-but-distinct logical units — e.g., two separate list items/repair entries in a merge-retrospective-style report, each meant to be delimited by a `"\n\n"` paragraph break — could still land inside the fixed character window purely by accident of length: a short preceding item, or a generously-sized window, lets a substring in one item and a substring in the very next (unrelated) item both fall within N characters of each other. A raw character count has no way to distinguish "these are bound in the same sentence/paragraph" from "they merely happen to be close together," since a verbose correct paragraph and a terse adjacent-but-unrelated one can straddle any fixed window either way. The blank-line check supplies the actual structural boundary (this repo's own paragraph/list-item separator) that the window alone cannot see, so it correctly rejects a pairing that's numerically "near" but logically in two different units — which is exactly the false-positive that would slip through if only the window condition were enforced.
